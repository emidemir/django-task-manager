*) I wanted my clients to be able to get serialized user data when reading, and just use the user id when writing. The solution and the explanation is the followings
 - Django REST Framework completely separates the logic for reading (serialization) and writing (deserialization) into two distinct methods.
 - When you want to send data out to the client (e.g., a GET request), you access 'serializer.data'. Under the hood, DRF loops through your fields and calls to_representation().
   By overriding this method, you intercepted the outgoing data and said, "Instead of sending the ID, use the UserSerializer to send the whole object."
 - When a client sends data in (e.g., a POST or PUT request), you pass that data to the serializer and call serializer.is_valid().
   During validation, DRF does not call to_representation(). Instead, it calls a completely different method: to_internal_value().
 - Because you defined the field like this: user = serializers.PrimaryKeyRelatedField(queryset=User.objects.all())
   You told DRF, "By default, handle reads and writes using the Primary Key (ID)."
   Since you only overrode to_representation, you only changed the read behavior. You left the write behavior completely untouched. 
   Therefore, when to_internal_value() runs during a POST request, it relies on the default behavior of PrimaryKeyRelatedField, which expects a simple integer ID, validates
   that the user exists in the database, and prepares it to be saved.

!!!!!-----!!!!!
You don't have to catch the serializer.is_valid(raise_exception=True) exception because drf will return HTTP 400 Bad Request responses by default.

 - Use select_related() when you are looking at:
   -> ForeignKey (A standard one-to-many relationship, but you are looking from the "many" side to the "one" side. e.g., getting a Book's author).
   -> OneToOneField

 - Use prefetch_related() when you are looking at:
   -> ManyToManyField
   -> Reverse ForeignKey (Looking from the "one" side to the "many" side. e.g., getting an Author and trying to fetch all their books using author.book_set.all()).

 - You have a leading slash (/) at the beginning in the string you are returning for the file path. Django's storage backends (including django-storages for MinIO/S3) expect upload_to paths to be relative. 
   When you provide a path that starts with a /, Django interprets it as an absolute path. For security reasons, Django prevents saving files to absolute paths to stop path traversal attacks 
   (i.e., someone trying to write files outside of your designated storage directory or bucket), and it throws a SuspiciousFileOperation.
